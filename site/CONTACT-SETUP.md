# Contact system setup (owner action required)

This feature is not live until a Pages preview and a real inbox delivery have been tested. Never commit email addresses, web-app URLs, secrets or tokens. Configure preview first; production deployment and production configuration are separate decisions. Form data passes through Cloudflare Pages Functions, Google Apps Script, and Google mail infrastructure. Review the draft privacy notice with counsel before adoption.

## 1. Google Apps Script

1. Sign in to the Google account that will send the mail. Create a standalone Apps Script project at script.google.com and paste the entire contents of `site/contact-setup/Contact.gs` into its script editor. Save it.
2. In Project Settings → Script Properties, add `CONTACT_RECIPIENT_EMAIL` with the private inbox address and `CONTACT_SHARED_SECRET` with a long random secret (at least 32 characters). Keep both private. Use a securely generated secret, not an example or password reused elsewhere.
3. Deploy → New deployment → Web app. Execute as the owner account; choose access **Anyone** so the Pages server can invoke it without an interactive Google sign-in. Authorize the requested MailApp permission as that account. Keep the resulting `/exec` URL private. The shared secret authenticates requests to this public endpoint; anyone who obtains it can send mail. Rotate it in both systems if exposed. Google account quotas and service availability apply.
4. Each script code change requires a new deployment version; update the `/exec` URL in Pages if it changes. Restrict editor access to the project. Script Properties are available to project editors, not a substitute for access control.

## 2. Cloudflare Pages preview

1. In Cloudflare Dashboard → Workers & Pages → streambridgeapp → Settings → Builds & deployments, inspect the Git connection, production branch, preview branch controls and build watch paths. Confirm the Git integration is connected. Do not change or deploy the production branch for this task.
2. Pages Functions requires `functions/` at the configured **project root**. These website-only files live at `site/functions/`; configure the Pages project root directory as `site` and the static build output directory as `.` (relative to that root), with no build command if the static site does not need one. Check the existing values and Cloudflare build log before changing them; root/output changes can affect production on its next deployment. Coordinate with the owner and test a preview first. The repository-root `functions/` directory would violate the website-only scope. Ensure the built artifact includes `index.html`, `contact/index.html`, `terms/index.html`, `privacy/index.html`, `news/index.html`, `party/index.html`, `_headers`, and assets. Pages should compile `site/functions/api` as Functions, not merely serve those files as static assets. Check build logs and test `/api/contact-config` JSON (not HTML/404) to confirm.
3. Under Settings → Variables and Secrets, set **Preview** environment secrets `CONTACT_GAS_WEB_APP_URL` (the Google `/exec` URL) and `CONTACT_SHARED_SECRET` (exactly the matching Script Property). Never add these to source, logs, screenshots or browser configuration. Deploy or retry a preview after setting values; changes need a new deployment to take effect.
4. Recommended: create a Cloudflare Turnstile widget and allow the preview hostname(s) being tested. Add the public `TURNSTILE_SITE_KEY` and secret `TURNSTILE_SECRET_KEY` to the Preview environment. The site key is returned to the browser; the secret is never returned. Set both or neither: a partial configuration disables the form. Without both, the form runs without Turnstile, using only a honeypot, size checks and same-origin checks; these are not rate limiting. Consider Cloudflare WAF rate limiting or equivalent protections separately, accounting for any plan limits. There is no durable per-IP rate limiter here.
5. Open the deployment's **commit-specific** preview URL reported in the Pages check and verify its SHA. Check `/contact` and `/contact/`, the other site routes, and both `/api/contact-config` and POST `/api/contact`. Confirm a malformed request fails, then submit a real message and check the private inbox, content and Reply-To. A success response means MailApp accepted the send request, not guaranteed inbox delivery. Timeouts and network failures can occur after sending; avoid blindly retrying an uncertain submission. Verify actual Gmail delivery before calling this live.
6. Confirm owner identity, authorized mailbox access, contact/grievance handling, retention/deletion including backups, processing locations and Turnstile use; update the draft notices and obtain qualified review. Monitor Gmail quotas and abuse. Do not publish private secrets or the inbox address.
